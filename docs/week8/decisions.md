## step1
블랙 프라이데이 행사를 앞두고, 주문 API 앞단에 대기열 시스템을 구축한다.
Redis Sorted Set을 활용해 진입 순서를 보장하고, 중복 진입을 방지한다.
유저는 대기열에 진입한 뒤, 자신의 순번과 예상 대기 시간을 조회할 수 있다.

### Q1. "예상 대기 시간"을 어떤 방식으로 계산할 예정인가요?

요구사항에 따르면 유저는 자신의 순번과 예상 대기 시간을 조회할 수 있어야 합니다. 순번은 Redis Sorted Set의  ZRANK
를 통해 쉽게 가져올 수 있지만, 대기 시간을 도출하기 위해서는 시스템의 처리량(Throughput) 기준이 필요합니다.

여기서 어떤 방식을 선택하느냐에 따라 구현 복잡도가 크게 달라집니다.

• 선택지 A: 고정 처리량 기반 계산 (단순 방식)
• 방식: 관리자가 미리 "우리 시스템은 1초에 10명(또는 1분에 600명)을 처리할 수 있다"고 고정값을 설정해둡니다.
• 계산:  (내 앞의 대기 인원 수) / (초당 고정 처리량) = 예상 대기 초
• 장점: 구현이 매우 단순합니다. 추가적인 통계용 Redis Key가 필요 없습니다.
• 단점: 실제 서버 상태나 유저들의 체류 시간에 따라 실제 통과 속도는 달라질 수 있으므로, 시간이 줄어들지 않거나
갑자기 크게 줄어드는 등 오차가 발생할 수 있습니다.
• 선택지 B: 동적 처리량 기반 계산 (정확도 우선 방식)
• 방식: 최근 N분 동안 대기열에서 실제로 빠져나가 주문으로 진입한(Active 상태가 된) 인원의 통계를 계산하여,
'현재 실제 초당 처리량'을 구합니다.
• 계산:  (내 앞의 대기 인원 수) / (최근 1분간의 실제 초당 처리량) = 예상 대기 초
• 장점: 시스템 상황이 느려지면 대기 시간도 늘어나게 되어, 유저에게 훨씬 정확하고 신뢰성 있는 예상 시간을
보여줍니다.
• 단점: 얼마나 많은 인원이 빠져나갔는지를 기록하기 위해 별도의 Redis 카운터나 캐시 로직을 추가로 구현해야
하므로 시스템 복잡도가 올라갑니다.

### Q2. '대기 상태(Waiting)'에서 '활성 상태(Active)'로의 전환 및 만료 정책은 어떻게 할까요?

유저가 대기열에서 본인 차례가 되었을 때, 실제 주문(결제) API를 호출할 수 있는 권한을 어떻게 부여하고 회수할
것인지에 대한 설계입니다. (이 경계가 명확해야 서버가 실제로 보호됩니다.)

• 선택지 A: 두 개의 저장소 분리 (Waiting Queue -> Active Set 이동 방식)
• 방식:
1. 대기 중인 유저는 Redis의  Waiting Queue(Sorted Set) 에 머뭅니다.
2. 백그라운드 스케줄러(예: 1초마다 실행)가  Waiting Queue 에서 가장 앞선 유저 N명을 꺼내어  Active Set 으로
이동시킵니다.
3. 주문 API는 유저가  Active Set 에 존재하는지만 검사합니다.
4. 유저가 결제를 완료하거나, 5분(TTL)이 지나면  Active Set 에서 강제 추방됩니다.
• 장점: 대기 중인 인원과 진입한 인원의 상태가 완벽히 분리되어 관리가 명확합니다. 실제 서버로 들어오는 트래픽
인원을 정확하게 제어할 수 있습니다.
• 단점: 주기적으로 큐를 이동시키는 스케줄러(Worker) 구현이 필수적입니다.
• 선택지 B: 단일 큐 + 커트라인 방식
• 방식:
1. 하나의  Queue(Sorted Set) 만 사용합니다. 점수(Score)는 유저의 진입 시간(Timestamp)입니다.
2. 서버에 글로벌 변수(또는 Redis Key)로  현재 입장 가능한 시간(Cut-off Time) 을 업데이트합니다.
3. 유저가 진입을 시도할 때, 본인의 Timestamp가  Cut-off Time 보다 이전이면 통과, 아니면 대기시킵니다.
• 장점: 데이터를 큐에서 넣고 뺄 필요가 없어 구현과 Redis 연산이 매우 단순합니다.
• 단점: 특정 유저가 들어왔다가 그냥 나가버린 경우(이탈)를 추적하기 어렵습니다. 만료 처리가 까다로워 정확히
동시에 몇 명이 들어왔는지 정밀하게 제어하기 힘듭니다.

## step2
스케줄러가 일정 주기로 대기열에서 N명씩 꺼내 입장 토큰을 발급한다.
토큰은 TTL이 있어 일정 시간 내 사용하지 않으면 자동 만료된다.
토큰이 있는 유저만 주문 API에 진입할 수 있으며, 주문 완료 후 토큰은 삭제된다.
처리량 설계 기준(DB 커넥션 풀, 평균 처리 시간)을 바탕으로 스케줄러의 배치 크기를 산정한다.

### 1️⃣ 문제 상황 재정의 (요구사항 재해석)
이 단계는 단순한 "토큰 발급"이 아니라, 데이터베이스와 결제 시스템의 병목 현상을 통제하기 위한 "수문(Floodgate)
제어" 문제입니다.

• 시스템 관점: 한정된 DB 커넥션 풀(Connection Pool) 자원을 고갈시키지 않으려면, 동시에 활성화될 수 있는 유저의
수(Active Token)를 수학적으로 제한해야 합니다. 이를 위해 시스템 처리량을 역산하여 스케줄러가 한 번에 통과시킬 적정
인원(N)을 찾아내는 것이 핵심입니다.
• 비즈니스 관점: 고객이 대기열을 뚫고 들어왔을 때, 결제 도중 튕기는 일이 없도록 쾌적한 전용 쇼핑/결제 시간을 보장해
주어야 합니다.
• 사용자 관점: 내 차례가 되었을 때 "언제까지 결제를 완료해야 하는가(TTL)"를 명확히 인지해야 하며, 중간에 오류가
났을 때 바로 쫓겨나는지 다시 시도할 수 있는지 예측 가능해야 합니다.

### Q1. [경계 설계] 입장 토큰 검증 로직을 애플리케이션의 어느 계층(Layer)에 둘까요?

대기열 시스템의 목적은 한정된 DB나 서버 자원이 터지지 않도록 보호하는 것입니다. 토큰(Active 상태)이 없는 유저가
주문 API( /api/v1/orders )를 호출했을 때, 이 요청을 어디서 끊어낼 것인가에 대한 결정이 필요합니다.

• 선택지 A: 웹 계층 (Spring Interceptor 또는 Filter)
• 방식: HTTP 요청이 Spring Controller에 도달하기 전, Interceptor에서 헤더나 토큰 값을 가로채어 Redis를
조회합니다. 토큰이 없으면 즉시  401 Unauthorized  또는  403 Forbidden 을 반환합니다.
• 장점:
• 애플리케이션의 깊은 곳(Service, DB Connection 등)까지 요청이 들어오지 않으므로 서버 자원(Tomcat 스레드,
메모리 등) 보호에 가장 효과적입니다.
• 주문 비즈니스 로직(Facade, Service)이 대기열 시스템의 존재를 알 필요가 없어 관심사의 분리(Separation of
Concerns) 가 명확해집니다.
• 단점: 보호해야 할 API 경로(URL)를 Interceptor 설정 파일에서 관리해야 하므로, API 경로가 변경되거나 추가될 때
설정 관리가 필요합니다.
• 선택지 B: 비즈니스 계층 (Facade 또는 Service 내부)
• 방식: Controller를 통과한 후,  OrderFacade.createOrder()  로직의 가장 첫 번째 줄에서 Redis를 조회하여
검증합니다.
• 장점: 해당 비즈니스 로직을 호출하는 곳이 어디든(웹 API이든, 내부 스케줄러이든) 항상 검증을 수행하므로
비즈니스 흐름상 누락될 위험이 적습니다.
• 단점: 토큰이 없는 비정상 요청도 Controller와 DTO 바인딩 과정을 거치고 비즈니스 계층까지 내려오게 되어,
불필요한 객체 생성과 연산이 발생합니다.

### Q2. [정책/예외] 결제(또는 주문) 실패 시, 발급된 토큰의 처리 정책은 어떻게 할까요?

유저가 대기열을 뚫고 입장 토큰(Active)을 받아 결제를 시도했습니다. 그런데 카드 잔고 부족이나 외부 PG사 오류 등으로
결제가 실패했을 경우, 이 유저가 가지고 있던 "입장 토큰"을 어떻게 처리할지가 UX와 시스템 가동률에 큰 영향을
미칩니다.

• 선택지 A: 결제 실패 시 즉시 토큰 강제 회수 (1회용 토큰)
• 방식: 결제 실패 응답을 주기 직전에 Redis에서 해당 유저의 Active 토큰을 삭제합니다. 유저는 결제를 다시 하려면
대기열 맨 뒤부터 다시 서야 합니다.
• 장점: 대기열 순환(회전율)이 극대화되고, 뒤에서 기다리는 사람들에게 가장 공정합니다. 악의적인 매크로가 토큰
하나로 무한정 재시도하는 것을 막습니다.
• 단점: 단순 카드 비밀번호 오타 등의 사소한 실수로 결제가 실패한 정상 유저가 다시 수십 분을 대기해야 하므로,
고객 경험(UX) 측면에서 매우 치명적인 불만이 발생할 수 있습니다.
• 선택지 B: 실패해도 TTL(예: 5분) 만료 전까지는 유지하여 재시도 허용
• 방식: 성공했을 때만 명시적으로 토큰을 회수(또는 무효화)하고, 실패 시에는 아무 조치도 하지 않아 유저가
자연스럽게 결제 수단을 변경해 다시 시도할 수 있게 둡니다.
• 장점: 결제 과정에서 문제가 생기더라도 주어진 5분 내에는 마음 편히 다시 시도할 수 있어 고객 경험이 훨씬
좋습니다.
• 단점: 한 번 Active 상태가 된 유저가 결제 실패 후 아무것도 안 하고 창을 켜둔 채 방치하면, 남은 TTL 시간 동안
슬롯 1개가 무의미하게 점유되어 뒤에 있는 사람들의 대기 시간이 미세하게 길어집니다.

### Q3. [스케줄러/시스템] 스케줄러 배치 크기(N) 산정 기준의 가정

요구사항에 **"처리량 설계 기준(DB 커넥션 풀, 평균 처리 시간)을 바탕으로 스케줄러의 배치 크기를 산정하라"**고 되어
있습니다. 이를 계산하기 위한 수식을 문서화해야 하는데, 제가 아래와 같은 기본 모델(수식)을 가정하고 문서에 기재해도도
괜찮을까요?

• 산정 공식:
초당 통과 인원(N) = DB 커넥션 풀 크기 / 평균 1건당 트랜잭션 소요 시간
• 가정치 적용 예시 (초기 추정치):
│ [스케줄러 배치 크기 산정 근거]
│
│ • 가용 DB 커넥션 풀: 10개 (HikariCP 기본값)
│ • 주문 트랜잭션 1건의 평균 소요 시간: 0.2초 (200ms) 로 가정
│ • 단일 커넥션의 초당 처리량(TPS): 1초 / 0.2초 = 5건
│ • 시스템의 이론상 최대 초당 처리량: 10개 × 5건 = 50건
│ • 안전율(Safety Factor): 결제 재시도 유저 및 조회 등 다른 API의 커넥션 점유를 고려해 가용량을 50%로 보수적 산정.
│ • 초기 추정 스케줄러 배치 크기(N): 50건 × 0.5 = 25명
│ • 결론 (가정치 기준): 스케줄러는 1초마다 대기열에서 25명씩 꺼내어 입장 토큰을 발급한다. (※ 주의: 이는 초기 추정치이며, 실제 측정 결과에 따른 최종 산정값은 하단의 'N=21'로 대체됩니다.)

### 7 설계의 잠재 리스크 및 대안 모색

1. 결제 처리 도중 TTL 만료 리스크
   • 문제: 유저가 결제 비밀번호를 누르느라 5분이 지났고, 이 사이에 토큰 TTL이 만료되어버렸는데, 결제 승인 요청이
   백엔드로 들어오는 엣지 케이스(Edge Case)가 발생할 수 있습니다.
   • 해결 대안: 대기열 토큰 우회(Bypass)는 서명 검증(Signature Verification)이 완료된 PG 서버 간 승인 콜백에만 엄격히 허용합니다. 사용자 결제 요청 및 주문 상태 조회 등 유저가 직접 호출하는 API에는 인증, 주문 소유권, 멱등성 검사를 기존과 동일하게 계속 적용하여 보안을 유지합니다. 또한 결제 콜백 및 상태 처리 로직에는 만료된 토큰, 위조된 콜백, 중복 콜백이 우회되지 않으며 승인 처리가 한 번만 반영됨을 보장하는 통합/단위 테스트 추가를 지시(추가)해야 합니다.
2. 스케줄러 단일 장애점(SPOF) 리스크
   • 문제: N명을 꺼내는 스케줄러를 담당하는 서버 인스턴스가 뻗어버리면, 대기열이 멈추고 아무도 쇼핑을 할 수
   없습니다. 반대로 스케줄러가 여러 서버에서 돌면 N명이 아니라 2N, 3N명씩 통과해버립니다.
   • 해결 대안: 스케줄러 자체에 Redisson 기반의 글로벌 락(Global Lock)을 걸어 여러 서버 중 단 1대의 인스턴스에서만
   스케줄러가 작동하도록 보장해야 합니다.

유저가 대기 중 현재 순번과 예상 대기 시간을 실시간으로 확인할 수 있는 API를 구현한다.

### 1️⃣ 요구사항의 문제 상황 재해석

요구사항은 단순한 조회 API 구현처럼 보이지만, 근본적인 문제는 다음과 같습니다.

• 사용자 관점: 대기열에 갇힌 유저는 "내가 언제 입장할 수 있는지" 몰라 답답함을 느끼고 서비스에서 이탈할 위험이
있습니다. 이탈을 막기 위해 예측 가능한 피드백이 필요합니다.
• 시스템 관점: 수만 명의 대기 유저가 "내 차례가 왔는지" 끊임없이(Polling) 질문할 것입니다. 이 무차별적인 트래픽이
자칫 백엔드 시스템(WAS, Redis)을 다운시키는 DDoS 공격처럼 작용할 수 있습니다. 즉, 이 부하를 어떻게 안전하게
통제하고 최적화할 것인가가 핵심 설계 과제입니다.

### 질문 1. 대기 인원에 따른 Polling 부하 통제 방식

수만 명의 사용자가 대기열에 진입하면, 언제 자신의 차례가 올지 확인하기 위해 끊임없이 서버로 순번 조회 API( GET
/position )를 호출(Polling)하게 됩니다. 이 때, 이 무차별적인 조회 트래픽을 시스템이 어떻게 통제하고 부하를 줄일
것인지 결정해야 합니다.

선택지 A: 서버 주도 동적 Polling (권장)
순번 조회 API의 응답( Response )에 클라이언트가 다음 번에 호출해야 할 시간 간격( nextPollingInterval )을 서버가
계산해서 내려주는 방식입니다.

• 작동 방식: 내 앞에 대기자가 1만 명 있다면 "10초 뒤에 다시 물어봐"라고 길게 주고, 내 앞에 100명 남았다면 "1초 뒤에
물어봐"라고 짧게 주는 등 서버가 상황에 맞게 제어합니다.
• 장점: 대기열이 길어질수록 불필요한 Polling 횟수를 획기적으로 줄여, 서버와 Redis의 부하를 능동적으로 방어할 수
있습니다.
• 단점: 클라이언트 측에서 서버가 주는  nextPollingInterval  값에 맞춰 동적으로 타이머(setTimeout 등)를 조정하는
로직을 추가로 구현해야 합니다.

선택지 B: 클라이언트 고정 Polling + 서버 Rate Limit
클라이언트는 서버 상황과 관계없이 무조건 고정된 주기(예: 3초)로 지속해서 찌르는 방식입니다.

• 작동 방식: 앱에 "3초마다 호출"이라고 하드코딩해 둡니다. 대신 서버나 API Gateway에서 동일 IP/유저의 호출이 너무
잦으면 429(Too Many Requests) 에러로 튕겨냅니다.
• 장점: 클라이언트 로직 구현이 단순합니다.
• 단점: 대규모 트래픽 상황에서는 거절(429) 응답을 내려주는 것조차 시스템(스레드 풀, 로드밸런서)에 부하가 될 수
있습니다. 대기열 최적화 관점에서 다소 수동적인 방어입니다.

### 질문 2. 대기 순번 통과 시 '입장 토큰 발급'의 책임 경계

사용자가 자신의 순번이 다가와서 대기열을 통과(Active)하게 되면, 실제로 결제나 핵심 API에 접근할 수 있는 권한인
**'입장 토큰'**을 받게 됩니다.
요구사항 중 *"토큰 발급 시 순번 조회 응답에 토큰 포함"*을 구현하기 위해, 이 토큰을 '누가 언제' 만들어서 저장할
것인지 책임을 나누어야 합니다.

선택지 A: 스케줄러가 백그라운드에서 발급, API는 조회만 (권장)
기존 시스템의 스케줄러(Worker)가 주기적으로 동작하여 N명씩 대기열(Waiting Queue)에서 빼낸 뒤 토큰(Active Set)을
발급하여 Redis에 미리 저장해두는 방식입니다.

• 작동 방식: 순번 조회 API( GET /position )는 오직 "내 토큰이 만들어져 있는지" Redis에서 읽어오기만 합니다.
만들어져 있다면 그 토큰을 응답에 내려줍니다.
• 장점: 대량의 Polling 요청을 받는 '조회 API'와 상태를 변경하는 '토큰 발급 로직'의 책임이 완전히 분리됩니다. 수만
명이 동시에 API를 찔러도 토큰 발급 시 동시성 이슈나 DB 락 병목이 발생하지 않습니다.
• 단점: 스케줄러 인프라가 필수적으로 동작해야 합니다 (다만 기존 요구사항 2.12에 백그라운드 스케줄러 전환 내용이
있어 자연스럽습니다).

선택지 B: 순번 조회 API가 직접 발급 (Lazy Issuance)
유저가 자신의 순번을 조회( GET /position )하는 바로 그 트랜잭션 내에서 발급하는 방식입니다.

• 작동 방식: 순번 조회 API를 호출했을 때  내 순번 <= N(현재 통과 가능한 커트라인)  인 경우, 그 자리에서 직접 토큰을
생성해 Redis에 저장하고 응답에 내려줍니다.
• 장점: 백그라운드 스케줄러 없이 클라이언트의 요청에만 의존하여 지연 발급(Lazy)하므로 구조를 직관적으로 짤 수
있습니다.
• 단점: 대량의 Polling 요청 속에서 특정 유저들이 거의 동시에 커트라인을 통과할 경우, '조회 API' 내에서 동시성
제어(누가 먼저 발급받을지) 처리를 해야 하며, 읽기 전용이어야 할 API가 상태를 변경하게 되어 역할이 무거워집니다.

### 질문 3. 예상 대기 시간 산출 방식

요구사항의 "예상 대기 시간 계산 로직"을 어떻게 산출할지에 대한 결정입니다.

선택지 A: 시스템 설정값 기반의 단순 연산 (권장)
Redis 등에서 측정한 '현재 내 순번(Rank)'을 '시스템이 초당 통과시키기로 설정한 인원수(N)'로 나누어 단순히
계산합니다.

• 작동 방식: 내 순번이 150번이고, 스케줄러가 1초에 30명씩 통과시키도록 설정되어 있다면 ->  150 / 30 = 예상 대기 5초
• 장점: 별도의 데이터 저장이나 복잡한 모니터링 로직 없이 메모리 상에서 즉시 연산 가능하여, Polling API 응답 속도
최적화에 가장 유리합니다.
• 단점: 실제 유저들이 결제를 얼마나 빨리 마치고 이탈하는지의 '실제 속도'를 반영하지 못하므로, 오직 '시스템
설정값'에 의존한 이론적인 시간입니다.

선택지 B: 실제 통과 메트릭 기반 동적 계산
최근 1분(또는 특정 시간) 동안 실제로 대기열을 통과하여 결제까지 성공/실패한 인원수의 평균 속도를 기록해두고, 이를
기반으로 계산합니다.

• 작동 방식: 모니터링 배치가 최근 1분간 TPS가 20건이었음을 계산해 Redis에 캐싱해두면 ->  150 / 20 = 예상 대기 7.5초
• 장점: 시스템의 실제 병목 상황이나 유저의 행동 패턴이 반영되어 고객에게 더 정확한 대기 시간을 안내할 수 있습니다.
• 단점: 실시간 통과/이탈 메트릭을 수집하고 집계하는 별도의 로직과 저장 공간(복잡도)이 추가로 요구됩니다.

### 1. 현재 구조 (대기열 기반 즉시 결제 모델)

대기열을 통과해 토큰(Active)을 발급받은 유저가 정해진 짧은 시간(TTL) 내에 주문과 결제를 모두 완료해야 하는
구조입니다. (예: 쇼핑몰의 한정판 스니커즈 선착순 판매 등)

#### 👍 장점 (Pros)
• 허수 예약(사재기) 최소화: 결제까지 즉시 완료해야 최종적으로 재고를 가져가므로, 돈을 내지 않고 재고만 묶어두는
악성 유저나 매크로를 방어하기 유리합니다.
• 시스템 로직 단순화: 예매만 해두고 도망간 유저(No-show)의 재고를 롤백(원복)하기 위한 복잡한 백그라운드 스케줄러나
취소표 처리 로직에 대한 부담이 적습니다.
• 확실한 재고 마감: 준비된 수량이 모두 결제되면 이벤트가 완전히 종료되므로, 운영 관점에서의 마감이 깔끔합니다.
#### 👎 단점 (Cons)
• 대기열 해소 속도 저하: 유저가 카드 번호를 입력하고 외부 PG사와 통신하는 '느린 시간' 동안에도 토큰을 쥐고 대기열
슬롯을 차지하게 됩니다. 이로 인해 대기 중인 다음 사람들의 입장 속도가 느려집니다.
• 외부 PG사 장애에 취약: 트래픽이 몰릴 때 PG사가 지연되면, 전체 시스템의 파이프라인(주문->결제)이 정체되어 버립니다.
• 유저 UX 스트레스: 초 단위 경쟁 속에서 결제 수단까지 빠르게 입력해야 하므로 유저의 피로도와 실수(결제 실패로 인한
탈락) 가능성이 높습니다.

### 2. 코레일 구조 (선점 후 사후 결제 모델)

대기열을 통과하면 재고(좌석)만 빠르게 선점 처리하고, 결제는 10~20분의 유예 시간을 주어 나중에 천천히 하도록 분리한
구조입니다. (예: 명절 기차표, 대형 콘서트 티켓팅 등)

#### 👍 장점 (Pros)

• 압도적인 예매 처리량(Throughput): 가장 느리고 병목이 심한 "PG사 결제"를 예매 과정에서 빼버렸기 때문에, 예매
자체는 Redis 등을 통해 0.1초 만에 끝납니다. 대기열이 놀라운 속도로 줄어듭니다.
• 트래픽(부하) 분산: 수만 명의 유저가 거의 동시에 예매를 완료하더라도, 결제는 유저마다 20분 내에 각기 다른 시간에
시도하므로 PG사나 결제 DB에 가해지는 트래픽이 넓게 분산됩니다.
• 편안한 유저 경험(UX): 일단 좌석을 확보했다는 안내를 받으면, 유저는 안심하고 여유롭게 결제 앱을 켜서 지불을 완료할
수 있습니다.

#### 👎 단점 (Cons)
• 복잡한 재고 복구(취소표) 아키텍처 필수: 유예 시간(20분) 동안 결제하지 않고 이탈한 유저를 찾아내어 예매를 취소하고,
잠겨있던 재고를 다시 시장에 풀어주는(Rollback) 견고한 스케줄러나 Redis TTL 로직이 반드시 구현되어야 합니다.
• 악의적인 재고 점유에 취약: 지불 능력이 없는 매크로 봇들이 일단 수만 개의 좌석을 선점만 해놓고 결제를 하지 않아,
진짜 구매하려는 유저가 표를 구하지 못하는 상황이 발생할 수 있습니다.
• 2차 트래픽 스파이크 발생: 이탈자의 미결제 표가 취소되어 풀리는 특정 시간(이른바 '취소표 줍기' 시간)에 또다시
수많은 유저가 몰려들어 서버 부하를 유발할 수 있습니다.

- n만명이 접속하면 n만개의 소켓 객체가 메모리에 상주
- 연결만 유지하더라도 비용이 큼
- n만명이 동시에 연결이 끊긴 후 재접속 시도 시 ddos 공격과 같은 원리로 서버 다운(thundering herd)
폴링
- stateles하기 때문에 별도의 유지 비용이 없음
- 요청이 처리되는 매우 짧은 시간만 자원을 쓰고 반납함
- 심지어 db가 아닌 redis 조회이기 때문에 조회 비용이 매우 낮음
단방향 상태 확인만 필요한 대기열 순번 조회에서는 양방향 실시간 연결을 유지할 필요가 없기 때문에 폴링이 더 효율적
  ### 1. 연결 유지 방식 (Stateful vs Stateless)
  • SSE (Server-Sent Events):
  • 웹소켓처럼 양방향 통신은 아니지만(서버 ➔ 클라이언트로 단방향), HTTP 연결을 끊지 않고 계속 열어두는(Persistent
  Connection) 방식입니다.
  • 즉, Stateful합니다. 10만 명이 대기열에 있다면 서버는 10만 개의 HTTP 커넥션을 메모리에 계속 유지해야 합니다.
  Spring MVC(Tomcat) 같은 동기식 스레드 모델에서는 스레드 고갈로 서버가 즉시 뻗어버릴 수 있으며, WebFlux(Netty)
  같은 비동기 모델을 쓰더라도 커넥션 객체 유지 및 파일 디스크립터(FD) 한계에 부딪히게 됩니다.
  • 폴링 (Polling):
  • 작성해주신 내용처럼 Stateless합니다.
  • 클라이언트가 3초에 한 번 요청을 보내고, 서버는 Redis에서 순번을 조회해 0.01초 만에 응답하고 연결을
  끊어버립니다. 서버는 연결 유지에 대한 부담이 전혀 없습니다.
  ### 2. Thundering Herd (동시 재접속 폭주) 문제
  • SSE:
  • 네트워크 불안정, 로드밸런서의 타임아웃, 혹은 배포로 인해 서버가 재시작되어 기존 연결이 끊어지는 순간, 10만
  명의 클라이언트가 동시에 재연결(Reconnect)을 시도합니다. 웹소켓과 완벽하게 동일한 원리로 서버 다운을 유발할 수
  있습니다.
  • 폴링:
  • 연결을 유지하고 있지 않으므로 이런 개념 자체가 없습니다. 각 클라이언트가 설정된 주기에 맞춰 개별적으로 요청을
  보내므로, Nginx나 로드밸런서 단에서 트래픽을 비교적 균일하게 분산 처리하기 쉽습니다.

  ### 3. 네트워크 오버헤드와 실시간성

  • SSE:
  • 최초 연결 시에만 HTTP 헤더를 주고받고, 이후에는 가벼운 이벤트 데이터만 지속적으로 밀어주기 때문에 네트워크
  오버헤드가 매우 적고 실시간성이 높습니다.
  • 폴링:
  • 매 요청마다 HTTP 헤더를 새로 맺고 끊어야 하므로 네트워크 대역폭이나 오버헤드가 상대적으로 큽니다.
  • 또한, 설정된 주기(예: 3초)만큼 순번 업데이트에 지연이 발생합니다.

  ### 💡 요약: 대기열 시스템에서는 무엇이 맞을까?

  결론부터 말씀드리면, "몇 만 명 이상이 겹치는 대규모 대기열"에서는 폴링(Polling)이 압도적으로 안전하고 효율적입니다.

  SSE는 단방향 상태 확인만 필요한 대기열의 요구사항과 잘 맞아떨어지는 기술처럼 보이지만, **"연결을 유지해야 한다"**는
  본질적인 특징 때문에 웹소켓이 가진 대규모 트래픽의 메모리/커넥션 유지 부담과 Thundering herd 문제를 그대로 안고
  있습니다.

  따라서 다음과 같이 기술을 선택하는 것이 일반적입니다.

  • 폴링(Polling): 코레일, 콘서트 예매처럼 트래픽이 예측 불가능할 정도로 폭주하여 서버 생존이 최우선일 때 (단, Redis
  조회를 통해 서버 연산 비용을 극단적으로 낮춰야 함)
  • SSE: 주식 호가창, 알림 시스템처럼 대상자가 한정되어 있고 즉각적인 실시간성이 훨씬 중요할 때

### 1. 더미 데이터 적재 완료
빠른 데이터 적재를 위해 Spring Data JPA 대신, 순수 JDBC의  executeBatch 와  rewriteBatchedStatements=true  옵션을
적용한 Java 스크립트를 작성하여 데이터를 일괄 삽입(Batch Insert)했습니다.
•  users  테이블: 10,000명 적재 완료
•  product  및  stock  테이블: 100,000건 적재 완료 (각 상품당 재고 10,000개)

### 2. K6 E2E 부하 테스트 진행 및 측정 결과

작성하신 E2E 시나리오(주문 생성  POST /api/v1/orders  -> 결제 요청  POST /api/v1/payments )를 기반으로 Virtual
User(VU) 50명으로 30초간 부하를 발생시켰습니다. PG 모듈 연동의 경우 가이드해주신 대로 비동기 처리로 동작합니다.

[측정 결과 요약]
• 총 실행 시나리오 (주문+결제 사이클): 1,311회
• API 총 요청 횟수: 2,622건
• 평균 응답 속도 (Latency): 약 79.77ms
• 종합 병목 TPS (주문+결제 1사이클 기준): 42.41 TPS

│ 💡 참고: PG 시스템 연동이 비동기로 분리(요청 지연 100500ms, 처리 지연 15s)되어 있어 API 자체의 HTTP 응답은 비교적
│ 빠릅니다. 하지만 주문 DB 트랜잭션과 Kafka 아웃박스 이벤트 발행 등이 엮인 종합적인 파이프라인 처리 능력이 1초당 약
│ 42건(사이클)을 처리하는 병목 지점으로 나타났습니다.

### 3. 스케줄러 통과 인원(N) 최종 산정

측정된 결과를 이론적 수식에 대입하여 최종 배치의 크기를 튜닝할 수 있습니다.

• 이론적 수식:  N = Min(주문 DB TPS, 결제 DB TPS, 외부 PG사 연동 TPS) * 스케줄러 주기 * 안전율
• 측정된 종합 병목 TPS: 42.41건/초
• 스케줄러 주기: 1초 (가정)
• 안전율: 0.5 (결제 실패(PG 40%) 및 한도 초과 등 재시도 트래픽을 고려한 50% 버퍼)

계산식:

│  N = 42.41 * 1 * 0.5 = 21.2

결론:
주문부터 비동기 결제 처리까지의 전체 파이프라인 병목을 고려했을 때, 대기열 스케줄러가 **1초마다 21명의
유저(N=21)**를 통과시키도록 튜닝하는 것이 시스템의 안정성을 유지하며 선착순 이벤트를 처리할 수 있는 최적의
설정입니다.
