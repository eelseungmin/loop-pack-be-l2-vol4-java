### Q1. [정책/경계] 좋아요 집계(Denormalization) 이벤트 분리 및 실패 시 처리 방식

상황 배경:
현재는 사용자가 상품에 '좋아요'를 누를 때 데이터 정합성을 위해 단일 트랜잭션 내에서 **비관적 락(Pessimistic
Lock)**을 걸고  PRODUCT  테이블의  like_count 를 증가시키고 있습니다.
이를  ApplicationEvent 를 통해 부가 로직으로 분리하면, 사용자의 '좋아요' 자체는 즉시 성공(빠른 응답)하지만
백그라운드에서  like_count 를 올리는 이벤트 처리는 일시적인 DB 락 대기 시간 초과나 장애로 인해 실패할 수 있습니다.
(즉, Eventual Consistency 적용)

질문:
이때, 백그라운드에서 실행되는 '좋아요 집계' 업데이트가 실패한다면 어떻게 처리하는 것이 서비스 정책에 맞을까요?

• (Recommended) 선택지 A: 에러 로그만 남기고 무시 (Best Effort)
• 설명: 이벤트 처리가 실패하면 에러 로그만 남기고 별도의 재시도를 하지 않습니다.
• 영향도: 실제 유저가 누른 좋아요 수와 상품에 노출되는  like_count  숫자에 미세한 오차가 발생할 수 있습니다.
하지만 통계적 의미가 강한 데이터이므로 약간의 오차를 허용하고, 시스템 구조를 단순하고 가볍게 가져갈 수 있습니다.
• 선택지 B: 실패 이벤트를 보관 후 스케줄러로 보정 (Guaranteed Delivery)
• 설명: 실패한 이벤트를  Outbox  패턴이나 별도의 실패 내역 테이블에 저장해두고, 5분 주기의 배치 스케줄러가 이를
읽어 다시 갱신을 시도합니다.
• 영향도: 숫자의 정확성을 100% 보장할 수 있습니다. 다만, 별도의 실패 테이블 설계와 스케줄러 구현이 필요하여
아키텍처가 다소 복잡해집니다.

### Q2. [정책] 서버 레벨 로깅(유저 행동)의 트랜잭션 단계(Phase) 결정

상황 배경:
사용자의 상품 조회, 클릭, '좋아요' 시도, 주문 시도 등의 행동 로그를 분석 목적으로 수집해야 합니다. 이 로깅 처리
또한 핵심 비즈니스 로직에 영향을 주지 않도록 이벤트로 발행하여 비동기로 처리하고자 합니다.

질문:
이러한 유저의 행동 로그를 남길 때, 대상이 되는 핵심 트랜잭션의 **성공 여부(Commit/Rollback)**와 로깅을 어떻게 연관
지어야 할까요?

• (Recommended) 선택지 A: 무조건 로깅 ( @EventListener  +  @Async )
• 설명: 트랜잭션의 성공/실패와 무관하게 사용자가 해당 액션을 호출한 즉시 이벤트를 발생시키고 로깅합니다.
• 영향도: 사용자가 주문을 '시도'했지만 재고 부족으로 실패한 경우에도 "주문 시도"라는 의미 있는 로그가 남습니다.
행동 자체(시도)를 분석하는 데 초점이 맞춰져 있습니다.
• 선택지 B: 트랜잭션 성공 시에만 로깅 ( @TransactionalEventListener(phase = AFTER_COMMIT)  +  @Async )
• 설명: 핵심 비즈니스 로직(예: 좋아요, 주문)의 트랜잭션이 완벽하게 성공(Commit)한 경우에만 로깅 이벤트를
처리합니다.
• 영향도: 시스템 상태가 실제로 변경된 '유효한 결과'만 로그로 남습니다. 실패한 시도는 로그에 남지 않으므로,
데이터베이스의 최종 상태와 완벽하게 일치하는 로그만 보관할 수 있습니다.

### Q3. [확장] 주문/결제 플로우 완료 후 부가 로직(알림 등) 실패 시 대응 정책

상황 배경:
결제가 성공적으로 완료되면 카카오톡 알림톡이나 앱 푸시 등으로 유저에게 '결제 완료 알림'을 발송하는 부가 로직을
이벤트로 분리합니다. 이는  @TransactionalEventListener(phase = AFTER_COMMIT) 을 사용하여 결제 DB가 커밋된 후
안전하게 트리거될 것입니다.

질문:
만약 외부 알림 서비스(카카오 등)의 일시적인 장애로 인해 알림 발송 이벤트 처리가 실패한다면, 이 실패를 어떻게 다루는
것이 좋을까요?

• (Recommended) 선택지 A: 에러 로그만 남기고 무시 (Fire & Forget)
• 설명: 외부 알림 발송에 실패하더라도 별도의 재발송 처리를 하지 않고 에러 로그만 남깁니다.
• 영향도: 사용자가 알림을 받지 못할 수는 있지만, 어차피 앱 내 주문 내역 화면에서 확인할 수 있습니다. 구조가
매우 단순해지고 시스템 리소스를 낭비하지 않으며 핵심 결제 로직에 전혀 영향을 주지 않습니다.
• 선택지 B: 실패 내역 저장 및 재발송 (Guaranteed Delivery)
• 설명: 알림 발송 실패 시 별도의 알림 실패 테이블에 기록해두고 배치 스케줄러로 재발송을 시도합니다.
• 영향도: 알림 도달률을 최대한 보장할 수 있습니다. 다만 앞선 '좋아요 집계'와 같이 실패 처리 테이블과 스케줄러가
추가되어 인프라 연동 구간이 다소 무거워질 수 있습니다.

### 1. 좋아요 집계 로직의 분리 (Eventual Consistency)
• 폭발적인 응답 속도 (UX 향상): 기존에는  PRODUCT  테이블의 특정 행에 비관적 락(Lock)을 걸고 숫자가 증가할 때까지
사용자가 기다려야 했습니다. 이벤트로 분리하면 "좋아요를 눌렀다"는 본인 데이터만 즉시 기록하고 200 OK를 반환하므로
체감 속도가 매우 빠릅니다.
• 병목 현상(Lock Contention) 제거: 특정 인기 상품에 수만 명의 트래픽이 몰리면(핫키 이슈) DB 락 대기로 인해 서버의
DB 커넥션이 고갈되어 전체 시스템이 멈출 수 있습니다. 집계를 비동기 이벤트로 뒤로 미루면 이런 동시성 병목이 완전히
해소됩니다.
• 장애 격리: 통계 수치를 올리는 과정에서 일시적인 DB 타임아웃이 발생해도 유저가 남긴 '좋아요 이력' 자체는 사라지지
않으므로, 유저 입장에서는 기능이 고장 났다고 느끼지 않습니다.
### 2. 결제 완료 알림 발송 분리 ( AFTER_COMMIT )
• 외부 장애로부터 핵심 로직 완벽 보호: 결제가 완료되어 카카오톡 알림 API를 호출했는데 카카오 서버가 응답하지
않는다고 가정해 보겠습니다. 이벤트로 분리하지 않았다면, 결제 성공 내역 자체가 롤백되어버리는 대참사가 일어날 수
있습니다. 이를 분리하면 외부 시스템(알림)이 죽더라도 '우리 서비스의 결제'는 안전하게 성공합니다.
• DB 커넥션 낭비 방지: 카카오톡 발송처럼 네트워크 I/O(외부 통신)가 발생하는 작업은 시간이 오래 걸립니다. 이 시간
동안 DB 커넥션을 쥐고 있으면 다른 유저가 결제를 못 합니다. 발송을 트랜잭션 바깥으로 분리하면 DB 커넥션을 즉시
반환하여 서버의 동시 결제 처리량이 비약적으로 상승합니다.
• 거짓 알림 방지:  AFTER_COMMIT  옵션을 쓰면, 결제가 완벽하게 성공으로 확정(Commit)되었을 때만 알림이 날아갑니다.
중간에 에러가 나서 롤백되었는데 유저에게 "결제 성공!" 문자가 가는 논리적 버그를 원천 차단합니다.

### 3. 유저 행동 서버 레벨 로깅 ( @EventListener )

• 진정한 데이터 자산 확보 (롤백과 무관한 수집): 유저가 '주문하기'를 눌렀으나 재고가 없어서 로직이 롤백되었다면,
일반적인 로깅에서는 기록도 함께 사라집니다. 하지만 이벤트를 사용하면 트랜잭션의 롤백과 무관하게 **"구매를
시도했다"**는 귀중한 마케팅 데이터(로그)를 유실 없이 수집할 수 있습니다.
• 관심사의 완전한 분리 (가독성/유지보수): 주문 비즈니스 코드 안에  kafkaTemplate.send() ,  log.info()  같은 인프라
코드가 덕지덕지 붙지 않습니다. 핵심 비즈니스는 "주문 완료 이벤트"만 던지고 본인 할 일만 깔끔하게 끝내므로 코드가
매우 우아해집니다.
• 메인 트랜잭션 성능 저하 제로: 비동기( @Async ) 스레드에서 로깅이 실행되므로, 로깅 서버가 느려지거나 분석용 DB에
부하가 생겨도 유저의 화면 전환 속도에는 0.1초의 영향도 주지 않습니다.

### 현업에서 로깅에 Outbox 패턴(전달 보장)을 강제하는 3가지 사례

#### 1. 과금 및 정산(Metering & Billing) 로그

가장 대표적인 사례입니다. 사용자의 특정 행동이 곧바로 '돈'과 직결되는 경우입니다.
• 사례 (클라우드 서비스, OpenAPI, AI 토큰 사용): AWS나 토스페이먼츠, OpenAI API 같은 서비스는 유저가 "API를 1회
호출했다"는 행동 로그 자체가 과금의 기준이 됩니다.
• 왜 필요한가? 만약 이 "호출 로그"를 외부 정산 시스템(Kafka 등)으로 쏘다가 네트워크 타임아웃으로 유실되면, 회사는
제공한 서비스만큼 돈을 청구하지 못합니다(매출 누수). 따라서 비즈니스 로직(API 제공)은 빠르게 응답하되, 호출했다는
로그는 같은 트랜잭션 내에서 Outbox 테이블에 찍어두고 무조건 수집 시스템으로 전달되게 보장합니다.
#### 2. 감사 로그 (Audit Trail) 및 개인정보 취급 로깅
금융권, 헬스케어, 혹은 사내 어드민(Admin) 시스템에서 법적으로 강제하는 보안/감사 로그입니다.
• 사례 (어드민의 고객 정보 열람, 비밀번호 변경 시도): 콜센터 직원이 고객의 개인정보나 결제 내역을 조회하는 행위.
• 왜 필요한가? 정보통신망법 등에 의해 "누가 언제 누구의 개인정보를 열람했는가"는 100% 보존되어야 합니다. 로깅
시스템(예: ELK 스택)이 잠시 죽어있다고 해서 로그가 날아가면 법적 제재를 받습니다. 반대로 로깅 시스템이 죽었다고
개인정보 조회를 막아버리면 콜센터 업무가 마비됩니다. 이럴 때 로컬 DB의 Outbox에 로그를 남겨두어 비즈니스 가용성과
법적 로깅 의무를 동시에 충족시킵니다.

#### 3. 매출(전환율)과 직결된 핵심 퍼널(Funnel) 로깅

단순한 클릭이 아니라, "결제 시도"나 "장바구니 담기"처럼 고객의 구매 의지가 명확히 드러난 행동입니다.

• 사례 (이커머스의 장바구니 유기, 결제 실패 추적): 유저가 결제 버튼을 눌렀으나 잔고 부족으로 실패한 경우.
• 왜 필요한가? 많은 이커머스 회사들은 이런 로그를 캐치해서 10분 뒤에 *"결제 중 문제가 생기셨나요? 10% 쿠폰을
드릴게요"*라는 자동화된 CRM 마케팅(리타겟팅)을 태웁니다. 이 마케팅의 전환율이 굉장히 높기 때문에, 이 "결제 실패
행동 로그"가 유실되면 곧 잠재 매출의 유실을 의미합니다. 따라서 중요한 퍼널 로그는 일반 클릭 로그보다 훨씬 엄격하게
수집을 보장합니다.

### 💡 현재 우리 서비스(감성 이커머스)에 적용한다면?

앞서 문서에 정의한 유저 행동 로깅 중에서도 데이터의 중요도(Value)에 따라 분리하는 것이 가장 우아한 설계입니다.

1. 상품 목록 조회, 일반 상품 클릭, 단순 좋아요 시도:
   • 👉 Outbox 불필요.  @Async 로 Kafka나 Logstash에 쏘고 실패하면 버림.
2. 주문 생성 시도, 결제 버튼 클릭(실패 포함):
   • 👉 고객의 CS 대응(왜 결제가 안됐나요?)과 리타겟팅 마케팅의 핵심이므로 Outbox 패턴 적용 고려.

### Q1. Consumer 측 이벤트 멱등성 처리 ( event_handled  테이블) 정책

이벤트가 중복 전송(At-Least-Once 특성)되거나 순서가 꼬여서 들어올 경우를 방어하기 위한 정책입니다. 어느 방식을
선호하시나요?

• (권장) 선택지 A:  event_handled  테이블로 1차 방어 + Version으로 2차 방어
• 내용: 수신한 모든 이벤트의 고유 ID(UUID)를  event_handled  테이블에 저장하여 중복 수신을 걸러내고, 순서가
역전된 이벤트는  product_metrics 의 Version( updated_at )으로 걸러냅니다.
• 영향도: 멱등성이 가장 확실하게 보장되어 안전합니다. 다만  event_handled  테이블의 데이터가 계속 쌓이므로,
추후 1~2주일이 지난 데이터를 지우는 주기적 삭제 배치를 고려해야 합니다.
• 선택지 B:  event_handled  테이블 없이 Version(발행 시간) 만으로 처리
• 내용: 이벤트 ID를 이력으로 남기지 않고, 단순히  product_metrics  테이블의  last_event_version (최종 업데이트
시간)보다 지금 들어온 이벤트의 발생 시간이 더 최신일 때만 덮어쓰기(Update)를 수행합니다.
• 영향도: 별도 멱등성 테이블 조회가 필요 없어 성능이 가장 빠릅니다. 단, "완전히 동일한 타임스탬프(밀리초까지
동일)를 가진 중복 이벤트"가 들어올 경우 필터링 로직이 까다로워질 수 있습니다.

### Q2. Transactional Outbox 이벤트 발행 정책

비즈니스 로직(예: 주문)과 함께 DB의  OUTBOX  테이블에 저장된 이벤트를, 실제로 Kafka로 어떻게 전송(Publish)할
것인지에 대한 정책입니다. 어느 방식을 선호하시나요?

• (권장) 선택지 A: 폴링(Polling) 스케줄러 방식
• 내용: Spring 애플리케이션 내에  @Scheduled 를 이용하여 매 1~3초마다  OUTBOX  테이블의 미발행( INIT ) 데이터를
읽어와 Kafka로 전송하고, 성공하면 상태를  PUBLISHED 로 업데이트합니다.
• 영향도: 별도의 인프라 구성 없이 애플리케이션 코드만으로 구현이 가능해 복잡도가 낮고 관리가 쉽습니다. 단,
스케줄러 주기(예: 1~3초)만큼 통계 갱신 지연(Latency)이 발생합니다.
• 선택지 B: Kafka Connect (CDC 기반) 활용 방식
• 내용: Debezium 같은 Kafka Source Connector를 별도로 띄워, DB의 Binlog(트랜잭션 로그)를 직접 감지해  OUTBOX
테이블에 Insert가 일어나는 즉시 Kafka로 전송합니다.
• 영향도: 지연이 거의 없는 실시간 전송이 가능합니다. 하지만 애플리케이션 외부에 Kafka Connect 인프라를 추가로
세팅해야 하므로, 개발 및 운영 복잡도가 크게 증가합니다.

> 해당 선택지에서 after-commit으로 발행할 때 @async를 붙이는 이유가 뭘까?

▸ Thought for 7s
Prioritizing Tool Usage
매우 좋은 질문입니다! 이 부분은 트랜잭션 경계와 쓰레드 분리를 이해하는 핵심 포인트입니다.
결론부터 말씀드리면, "메인 비즈니스 로직의 응답 속도(성능) 저하를 막고 시스템 장애를 격리하기 위해서" 입니다.
자세한 이유는 다음과 같습니다.
### 1. 왜  AFTER_COMMIT  인가?
만약 DB 커밋 전에 Kafka로 이벤트를 바로 전송해 버린다고 가정해 보겠습니다. 카프카 전송은 성공했는데, 직후에 DB
커밋이 실패(예: 데드락, 유니크 제약조건 위반)해서 롤백된다면 어떻게 될까요?
시스템 DB에는 데이터가 취소되었는데, 카프카에는 이미 이벤트가 발송되어 다른 시스템(집계/알림 등)이 동작해버리는
고스트 데이터(데이터 불일치) 가 발생합니다.
따라서 "DB에 완전히 반영된 것이 확인된 후(AFTER_COMMIT)" 에만 이벤트를 발행해야 합니다.
### 2. 왜  @Async  도 함께 붙이는가?
스프링의  @TransactionalEventListener(AFTER_COMMIT) 은 커밋 직후에 실행되긴 하지만, 기본적으로는 메인 트랜잭션과
동일한 쓰레드에서 동기적으로 실행됩니다.
만약  @Async  없이 Kafka 전송 로직이 실행된다면, Kafka 브로커 상태가 안 좋아서 타임아웃(예: 3초)이 발생할 때
사용자에게 API 응답을 내려주는 시간도 똑같이 3초가 지연됩니다. 이런 일이 반복되면 웹 서버(Tomcat)의 쓰레드가 모두
고갈되어 시스템 전체가 뻗어버릴 수 있습니다.
그래서  @Async 를 붙여 별도의 쓰레드(비동기)로 책임을 넘기고, 메인 쓰레드는 사용자에게 즉시 "주문 완료!" 응답을
내려주도록 분리하는 것입니다.
──────
### ⚠️ 여기서 등장하는 Outbox 패턴의 존재 이유

그런데  @Async 를 붙여 비동기 쓰레드로 Kafka에 던질 때 치명적인 문제가 하나 남습니다. 만약 비동기 쓰레드가 Kafka로
전송하려는 찰나에 서버 전원이 나가거나 앱이 죽어버리면 어떻게 될까요? 이벤트가 영영 유실됩니다.

그래서 앞서 질문드린 Outbox 패턴 (선택지 A) 이 등장하는 것입니다.

1. 메인 트랜잭션 안에서  주문 데이터 와 함께  Outbox 데이터(INIT 상태) 를 DB에 같이 저장합니다. (메인 쓰레드)
2. 트랜잭션이 커밋된 직후( AFTER_COMMIT )에,  @Async 를 통해 즉시 Kafka로 전송을 시도합니다. (비동기 쓰레드)
3. 만약 성공하면 DB의 Outbox를  PUBLISHED 로 갱신합니다.
4. 만약 실패하더라도, DB에  INIT  상태로 안전하게 남아있으므로 1~3초 주기의 폴링 스케줄러가 이를 주워서 재발송해
   줍니다. (이벤트 유실 완벽 방지)

### Q3. Kafka 파티션 키(Partition Key) 할당 전략

Kafka로 이벤트를 전송할 때, 어떤 키를 기준으로 파티션을 분배할지 결정해야 합니다. Consumer가 동일한 파티션의
메시지를 처리할 때는 순서가 보장됩니다.

• (권장) 선택지 A:  product_id 를 파티션 키로 사용
• 내용: 동일한 상품(product_id)에 대한 이벤트는 무조건 같은 파티션(그리고 같은 Consumer)으로 들어가게 합니다.
• 영향도: "A상품 조회수 증가 -> A상품 좋아요 증가" 같은 상품 단위의 이벤트 처리 순서가 완벽하게 보장되어 구현이
직관적입니다. 단, 특정 핫 인기 상품(예: 선착순 이벤트 상품)에 트래픽이 몰리면 특정 파티션에 부하가 집중되는(Hot
Partition) 문제가 발생할 수 있습니다.
• 선택지 B: 파티션 키 없이 라운드 로빈(Round-Robin) 무작위 분산
• 내용: 특정 키를 지정하지 않고, 모든 파티션에 골고루 트래픽을 뿌립니다.
• 영향도: 핫 파티션 문제 없이 부하가 완벽하게 분산되어 성능에 유리합니다. 단, Consumer 측에서 순서가 완전히
섞여서 들어오므로,  Q1 에서 정한 Version(발행 시간) 덮어쓰기 로직에 전적으로 의존해야 하며, 동시 처리 시 DB 락
경합 등 동시성 제어가 훨씬 까다로워집니다.

### 1.  acks=all  (메시지 유실 방지)
프로듀서가 Kafka 브로커로 메시지를 보낸 후, **"브로커가 메시지를 안전하게 잘 받았다고 응답(Ack)을 줄 때까지 얼마나
기다릴 것인가?"**를 결정하는 옵션입니다.
•  acks=0 : 메시지를 던지기만 하고 잘 받았는지 확인하지 않습니다. (매우 빠르지만, 브로커가 죽으면 메시지가 영원히
유실됨)
•  acks=1 : 카프카의 리더(Leader) 브로커가 메시지를 받았다고 할 때까지만 기다립니다. (리더가 메시지를 받고
복제본(Follower)에게 넘겨주기 직전에 죽어버리면 역시 메시지가 유실됨)
•  acks=all  (또는  -1 ): 리더 브로커뿐만 아니라, 모든 복제본(Follower) 브로커들까지 메시지를 완벽하게
복사(Sync)하여 저장할 때까지 기다립니다.
• 효과: 속도는 가장 느리지만, 카프카 서버 한두 대가 불시에 꺼지더라도 데이터가 절대 유실되지 않는 강력한
안정성을 보장합니다.
### 2.  idempotence=true  (메시지 중복 발행 방지)

이 옵션은 네트워크 오류 등으로 인해 프로듀서가 같은 메시지를 두 번(중복) 보내는 것을 카프카 브로커가
막아주는(멱등성 보장) 기능입니다.

• 문제 상황: 프로듀서가 브로커로 메시지를 보냈고, 브로커는 DB에 잘 저장했습니다. 그런데 브로커가 프로듀서에게 "잘
받았어!(Ack)"라고 대답하는 순간 네트워크가 끊겼습니다.
• 프로듀서 입장에서는 응답을 못 받았으니 "아, 전송 실패했구나" 하고 똑같은 메시지를 한 번 더 보냅니다(재시도).
결과적으로 카프카에는 동일한 메시지가 2개 쌓이게 됩니다.
• 해결책 ( idempotence=true ): 이 설정을 켜면 프로듀서가 메시지를 보낼 때 **고유한 번호(Producer ID + Sequence
Number)**를 꼬리표로 붙여서 보냅니다.
• 효과: 브로커가 메시지를 받을 때 꼬리표 번호를 기억해둡니다. 만약 네트워크 에러로 프로듀서가 똑같은 번호의
메시지를 다시 보내면, 브로커가 "어? 이거 아까 받은 번호네?" 하고 저장하지 않은 채 "잘 받았어(Ack)"라고 대답만
돌려줍니다. 즉, 프로듀서가 몇 번을 재시도하든 카프카에는 메시지가 딱 1번만 안전하게 저장됩니다.

──────
요약하자면:
우리 시스템의 Outbox 폴링 스케줄러가 이벤트를 Kafka로 쏠 때,

•  acks=all  덕분에 **"이벤트가 전송 도중 증발하지 않고 완벽하게 저장됨"**을 보장받고,
•  idempotence=true  덕분에 **"스케줄러가 재시도하더라도 토픽에 동일한 이벤트가 2개 생기지 않음"**을 보장받습니다.

> aggregate id는 용도가 뭐지?

▸ Thought for 3s
Prioritizing Tool Usage
aggregate_id 는 주로 도메인 주도 설계(DDD)와 이벤트 소싱 패턴에서 많이 사용하는 개념으로, 쉽게 말해 **"이 이벤트가
도대체 어떤 데이터(주체) 때문에 발생한 것인지 가리키는 식별자(PK)"**입니다.

Outbox 테이블에서  aggregate_id 와  aggregate_type 을 함께 두는 이유는 다음과 같은 아주 중요한 실무적 이점
때문입니다.
### 1. 파티션 키(Partition Key)로 활용 (가장 큰 이유)
우리가 앞서 **"Kafka로 이벤트를 쏠 때  product_id 를 파티션 키로 쓰자"**고 결정했었죠.
스케줄러가  OUTBOX_EVENTS  테이블을 읽어서 카프카로 보낼 때, 파티션 키를 알아야 합니다다

• 만약  aggregate_id  컬럼이 없다면? 스케줄러는  payload  컬럼에 들어있는 긴 JSON 텍스트를 매번
역직렬화(Parsing)해서 그 안에서  product_id 를 파헤쳐 꺼내야 합니다. 이는 성능을 크게 저하시킵니다.
• 해결책: 아예 이벤트를 저장할 때  aggregate_id  컬럼에  product_id (예: 100)를 명시적으로 박아두면, 스케줄러는
JSON을 뜯어볼 필요 없이  aggregate_id = 100 을 그대로 Kafka의 파티션 키로 넘겨주면 됩니다. 매우 빠르고 효율적입니다.

### 2. 디버깅 및 추적 (Traceability)

만약 카프카 장애나 알 수 없는 이유로 특정 이벤트 전송이 계속 실패해서 에러 로그가 찍힌다고 가정해 보겠습니다.
이때 DB를 열어봤을 때  payload  JSON만 덩그러니 있다면 어떤 주문, 어떤 상품에서 문제가 생겼는지 한눈에 파악하기
어렵습니다.
하지만  aggregate_type = 'ORDER' ,  aggregate_id = '5001'  이라고 적혀 있다면, "아, 5001번 주문에서 발생한 결제
완료 이벤트가 안 넘어가고 있구나!" 하고 직관적으로 파악하고 즉시 대응할 수 있습니다.

### 3. 도메인(Aggregate)별 순서 보장

만약 "특정 주문(Order)"에 대해 발생한 여러 이벤트(예: 주문 생성 -> 결제 완료 -> 부분 취소)를 순서대로 추적하거나
보정해야 할 때,  WHERE aggregate_id = 5001 ORDER BY id ASC  처럼 쿼리 한 줄로 특정 엔티티의 생애 주기(이벤트
히스토리)를 쉽게 뽑아볼 수 있습니다.
──────
결론적으로  aggregate_id 는 **"이 이벤트의 주인이 되는 엔티티의 PK"**를 담아두어, 성능(Kafka 파티션 키 지정)과
유지보수성을  대화하기 위해 설계된 컬럼입니다!

> event handled 테이블은 용도가 뭐지?

▸ Thought for 2s
Prioritizing Tool Usage
EVENT_HANDLED  테이블은 쉽게 말해 "메시지 중복 처리 방지용 방패(멱등성 보장)" 역할을 하는 아주 핵심적인
테이블입니다.
이 테이블이 왜 필요한지, 어떤 원리로 동작하는지 설명해 드리겠습니다.
### 1. 카프카의 근본적인 한계 (At-Least-Once)
우리가 설정한 카프카(분산 메시지 큐)는 안정성을 위해 기본적으로 적어도 한 번(At-Least-Once) 전송을 보장합니다.
이는 "메시지가 유실될 일은 절대 없지만, 간혹 똑같은 메시지가 2번 이상 전달될 수는 있다"는 뜻입니다.
• 문제 발생 시나리오:
1. Consumer(집계 서버)가 카프카로부터 '상품 A 좋아요 +1' 이벤트를 받습니다.
2. DB의  PRODUCT_METRICS  테이블을 업데이트( total_likes + 1 ) 합니다.
3. 이제 카프카에게 "나 잘 처리했어(Ack 커밋)" 라고 대답을 해야 하는데, 대답하기 직전에 서버가 일시적으로
다운되거나 네트워크가 끊깁니다.
4. 카프카는 "어? 얘가 처리를 못 했나 보네?" 하고 똑같은 '+1' 이벤트를 다시 보냅니다.
5. 결국 Consumer는 좋아요를 한 번 더 더하게 되어(+2) 통계가 뻥튀기되는 심각한 오류가 발생합니다.


### 2.  EVENT_HANDLED  테이블의 해결책 (Exactly-Once 구현)

이런 중복 수신을 막기 위해 발행자(Producer)는 모든 이벤트에 **절대 겹치지 않는 고유 번호(UUID)**인  event_id 를
붙여서 보냅니다.

Consumer가 이벤트를 받으면 다음 순서로 트랜잭션을 실행합니다.

1. 가장 먼저  EVENT_HANDLED  테이블에 해당  event_id 가 존재하는지 조회(또는 INSERT 시도)합니다.
2. 만약 이미 테이블에 있는 번호라면?
   • "아, 이거 예전에 처리했는데 카프카가 헷갈려서 또 보냈구나!" 하고 알아차립니다.
   • 집계 로직(+1)은 무시하고, 카프카에게 "어 알았어(Ack)" 하고 응답만 해주고 넘겨버고 니다.
3. 테이블에 없는 새로운 번호라면?
   • 진짜 처음 온 이벤트이므로  PRODUCT_METRICS 의 수치를 +1 해줍니다.
   • 그리고 다음에 또 똑같은 게 올 것을 대비해  EVENT_HANDLED  테이블에 해당  event_id 를 쾅 기록해 둡니다.
   • (중요) 이 통계 업데이트(+1)와 이력 기록(INSERT)은 반드시 하나의 DB 트랜잭션으로 묶여서 처리(All-or-
   Nothing)되어야 합니다.

결론:
EVENT_HANDLED  테이블은 네트워크나 인프라 장애로 인해 이벤트가 여러 번 들어오더라도 집계 수치는 정확히 한 번만
증가하도록 완벽하게 방어해 주는 기록 장부입니다.

### 1. 시스템 내부에만 머물러야 하는 이벤트 (ApplicationEvent)
스프링의  ApplicationEvent 는 기본적으로 내 애플리케이션(Commerce API) 내부에서 모듈 간의 결합도를 낮추기 위해
사용됩니다. 외부 시스템(Kafka)으로는 나갈 필요가 없는 이벤트들입니다.

• 예시 1 (내부 캐시 무효화): 어드민이 상품 정보를 수정해서  ProductUpdatedEvent 가 발생했습니다. 이 이벤트는 내
서버 메모리에 있는 로컬 캐시를 지우는 데만 쓰이면 됩니다. 다른 시스템은 알 필요가 없습니다.
• 예시 2 (회원가입 후 장바구니 생성): 유저가 가입해서  UserJoinedEvent 가 발생했습니다. 같은 커머스 API 내부에 있는
장바구니 모듈이 이 이벤트를 듣고 빈 장바구니를 하나 만들어줍니다.
• 이런 이벤트들까지 전부 DB Outbox 테이블에 넣고 Kafka로 쏘게 되면, 불필요한 네트워크 비용이 낭비되고 Kafka 토픽이
쓰레기 데이터로 가득 차게 됩니다.

### 2. 시스템 간 전파가 필요한 이벤트 (Kafka 발행 대상)

반대로, 내 시스템(Commerce API)이 아닌, 완전히 분리된 다른 시스템(Collector나 알림 서버 등)에서 후속 처리를 해야
하는 이벤트들입니다.

• 예시 1 (좋아요/조회 통계 집계): 유저가 좋아요를 눌러서  ProductLikedEvent 가 발생했습니다. 이 데이터는 Commerce
API가 아니라, 분리된 Commerce-Collector 시스템이 통계를 내기 위해 반드시 알아야 합니다. (현재 과제의 타겟입니다)
• 예시 2 (결제 완료 및 배송 시작): 결제가 성공해서  OrderCompletedEvent 가 발생했습니다. 이 사실은 외부에 있는
배송/물류 시스템이나 정산 시스템이 알아야 배송을 시작하고 돈을 나눌 수 있습니다.

### 요약하자면

요구사항의 해당 문구는 **"Step 1에서 로직을 분리하려고 만든 모든  ApplicationEvent 를 무지성으로 Kafka로 다 쏘지
말고, 그중에서 Commerce-Collector 시스템(외부)이 통계 집계를 위해 반드시 필요한 이벤트(주문 완료, 좋아요, 조회
등)만 선별해서 Outbox 테이블에 담아 Kafka로 발행하라"**는 아키텍처적 책임을 묻는 것입니다.

### 5️⃣ 잠재적 장애 시나리오 분석 (3가지)
① Redis 전체 장애 시 (TTL 이벤트 유실)
• 상태 불일치: 결제 타임아웃 발생 후, 상태를 보정해 줄 10초 TTL 이벤트가 트리거되지 않아 결제가 영원히  READY 로
남습니다.
• 데이터 정합성 및 복구: 최후의 보루인 30분 주기의 Fallback 스케줄러가 존재하므로 결국엔 환불/취소로 상태가
수렴됩니다. 시스템 복원력(Resilience)이 높습니다.
② 콜백 웹훅과 Redis TTL 보정 배치의 충돌 (Race Condition)
• 상태 불일치: PG 서버 지연으로 10초 뒤 TTL 보정 로직이 돌아 PG 상태 조회를 통해  APPROVED  업데이트를 치려는 순간,
동시에 밀려있던 PG 콜백 웹훅이 날아와서  handleCallback  트랜잭션을 시작합니다.
• 데이터 정합성 리스크: 두 쓰레드가 동시에 동일한 결제 건을 성공 처리하려고 진입합니다. 상태가 단순  READY  ->
APPROVED  로 갱신되는 것 외에, 결제 성공 알림 이벤트나 통계 데이터 집계가 2번씩 중복 실행될 가능성이 농후합니다.

③ 보상 트랜잭션 자체의 실패 (보상 실패 리스크)

• 상태 불일치: PG사 호출이 타임아웃 되어 내부에서 주문 상태를  CANCELED 로 바꾸고 쿠폰을 반환(보상)하려는데, 이때
DB 커넥션이 고갈되어 쿠폰 반환 트랜잭션이 실패합니다.
• 데이터 정합성 및 복구: 결제는 실패했는데 쿠폰은  USED 로 남아 고객이 손해를 보는 치명적 불일치가 발생합니다. 이
"보상 로직의 실패"를 재처리하기 위한 메커니즘(예: 보상 로직도 Outbox에 담기)이 누락되어 있습니다.

### 6️⃣ 시스템 일관성을 위한 설계 선택지 제안

현재 아키텍처는 보상 트랜잭션과 Eventual Consistency를 적극 도입한 훌륭한 분산 시스템 설계입니다. 다만, 식별된
**"동시성 충돌"**과 "보상 실패" 리스크를 해결하기 위해 다음과 같은 대안을 고려해 볼 수 있습니다.

선택지 A: 상태 전이 시 낙관적 락(Optimistic Lock) 도입

•  PAYMENTS  테이블 갱신 시  version  컬럼을 체크하여, 콜백이든 TTL 스케줄러든 먼저 도착한 녀석 하나만  READY ->
APPROVED 로 상태를 갱신하게 만듭니다. 나중에 도착한 트랜잭션은  OptimisticLockingFailureException 을 맞고
튕겨나가므로 콜백 중복 처리 리스크를 매우 깔끔하게 막을 수 있습니다.
• 운영 부담: 코드상  @Version 만 추가하면 되므로 복잡도가 낮습니다.

선택지 B: 보상 트랜잭션의 비동기 & 발행 보장 (Outbox 확장)

• 동기적인 try-catch로 보상 로직을 실행하지 않고, '결제 실패 이벤트' 자체를 Kafka Outbox에 발행하여 결제 취소, 쿠폰
복구, 재고 복구 컨슈머들이 각각 비동기로 확실하게(At-Least-Once) 처리하도록 위임합니다.
• 운영 부담: 파이프라인의 견고함은 극대화되지만, 보상 로직까지 컨슈머로 쪼개야 하므로 구현 복잡도가 크게 증가합니다.
선택지 C: 콜백과 보정 로직을 단일 이벤트 큐로 합치기

• 콜백 API나 TTL 이벤트가 직접 DB를 수정하지 않고, 수신 즉시 Kafka  payment-result  토픽에 메시지로만 던집니다.
유일한 단일 컨슈머 1대가 파티션 단위로 순차적으로 메시지를 뽑아 DB를 갱신하게 하여 동시성 경합 자체를 원천
차단합니다.
• 운영 부담: 아키텍처 일관성은 뛰어나나, 외부 PG 콜백 처리마저 카프카 큐를 타야 하므로 결제 승인 확인 지연 시간이
미세하게 늘어납니다.

### 1️⃣ Redis 전체 장애 시 (TTL 이벤트 유실) -> 🟢 완벽하게 구현됨
• 구현 상태:  PaymentFallbackScheduler 와  PaymentFacade.retryOrCompensatePayment(paymentId, true)  메서드를 통해
아주 훌륭하게 구현되어 있습니다.
• 코드 확인 내용:  isFallback  플래그가  true 로 넘어왔을 때 PG사 상태가  APPROVED (결제 성공)라면, 코드가 내부
DB를 업데이트하는 대신  paymentGateway.cancelPayment() 를 호출해 **PG 결제를 환불(취소)**시켜버립니다.
• 평가: 문서에 있던 설계(30분 뒤면 배송 지연 등의 이슈로 돈을 돌려주는 정책)가 코드에 그대로 녹아들어 있어 데이터
정합성을 완벽히 맞추고 있습니다.

### 2️⃣ 콜백 웹훅과 Redis TTL 보정 배치의 충돌 (Race Condition) -> 🔴 미구현 및 리스크 존재
• 구현 상태: 현재  PaymentV1Controller 에는 PG사 결제 요청 API( processPayment )만 있고, 아직 콜백을 수신하는 API가
구현되어 있지 않습니다.
• 코드 리스크: 추후 콜백 API를 추가할 때 반드시 주의해야 할 점이 보입니다.  PaymentModel  등 결제 도메인 객체를
확인해 보니  @Version 을 이용한 **낙관적 락(Optimistic Lock)**이 선언되어 있지 않습니다.
• 평가: 현재 코드 상태로 콜백 API만 덜렁 추가하게 되면, 콜백과 10초 뒤 TTL 보정 스케줄러가 동시에 DB의 결제 상태를
READY 에서  APPROVED 로 변경하려고 경합할 때 막아줄 방어막(Lock)이 없는 상태입니다. (추후  @Version  추가가
시급합니다)
### 3️⃣ 보상 트랜잭션 자체의 실패 (보상 실패 리스크) -> 🟡 구현은 되었으나 부분 실패 위험 존재

• 구현 상태:  PaymentFacade.retryOrCompensatePayment  코드 내부에서 결제 실패 처리 후  productFacade.
increaseStocks() (재고 복구)와  couponIssue.restore() (쿠폰 복구)를 동기적으로 순차 호출하도록 구현되어 있습니다.
• 코드 리스크: 이 메서드는 거대한 하나의  @Transactional 로 묶여 있습니다. 만약 30분 Fallback 스케줄러가 돌아서
PG사에 환불( cancelPayment )을 성공했는데, 그 직후 쿠폰 서버 장애로  restore() 가 에러를 던지면 어떻게 될까요?
• 트랜잭션이 롤백되어 우리 DB의 결제 상태는 여전히  READY 로 남습니다.
• 하지만 유저의 카드는 이미 환불되었습니다.
• 다음에 스케줄러가 또 돌면 이미 취소된 PG 거래를 또 취소하려고 하거나, 무한 루프에 빠질 수 있습니다.
• 평가: 보상 트랜잭션(재고/쿠폰 복구) 중 하나라도 실패하면 전체가 롤백되는 현재의 **동기 방식(try-catch 없이
던짐)**은 분산 환경에서 꽤 위험합니다. 실패 시 Outbox에 남기거나  try-catch 로 묶어 이벤트를 발행하는 식의 방어
코드가 추가로 필요해 보입니다.

### 🎯 첫 번째 질문: 동시성(Race Condition) 방어 정책

[상황 설명]
결제 요청 후, 네트워크 지연으로 인해 **"10초 뒤에 실행되는 Redis TTL 상태 보정 스케줄러"**와 **"PG사가 뒤늦게 쏴준
비동기 콜백(Webhook)"**이 0.01초 차이로 동시에 우리 서버에 도달했습니다.
두 로직 모두 DB의 결제 상태를  READY 에서  APPROVED 로 변경하고 주문을 확정 지으려 경합합니다. 중복 처리가 되면
통계 집계나 알림이 두 번 발송될 위험이 있습니다.
이 충돌을 어떤 방식으로 제어하는 것이 현재 프로젝트의 핏(Fit)에 가장 잘 맞을까요?

• 선택지 A: 낙관적 락 ( @Version ) 도입
• 방식: DB 업데이트 시 버전을 체크하여, 둘 중 나중에 커밋 시도하는 쪽을 강제로 튕겨내고(
OptimisticLockException ) 에러를 조용히 무시(Swallow)합니다.
• 장단점: 구현이 가장 쉽고 빠릅니다. 단, 동시 도달 시 에러 로그가 남을 수 있습니다.
• 선택지 B: 분산 락 ( Redisson ) 동기화
• 방식: 결제 요청 시 사용했던 분산 락( payment:lock:{orderId} )을 콜백 로직과 스케줄러에도 똑같이 걸어, 반드시
한 줄 서서 처리되도록 강제합니다. (선행 트랜잭션이 상태를 바꾸면 후행 트랜잭션은 아무것도 안 함)
• 장단점: 시스템 동작이 예측 가능하고 깔끔하지만, Redis 의존도와 락 대기 시간이 발생합니다.
• 선택지 C: 콜백 큐잉 (단일 큐 단일 처리)
• 방식: 콜백을 수신하면 즉시 200 OK 응답만 주고 메시지를 내부 큐(Kafka/Redis)에 밀어 넣습니다. 단 1대의
컨슈머가 큐에서 순차적으로 꺼내 DB를 갱신합니다.
• 장단점: 동시성 문제가 원천 차단되고 응답성이 최고지만, 큐 인프라 설정 등 구현 복잡도가 크게 올라갑니다.
어느 선택지로 구현(또는 설계) 방향을 잡을까요? 편하게 골라주시거나 다른 의견을 주셔도 좋습니다!

### 1. 카프카의 기본 동작: 자동 커밋 (Auto Ack)
카프카 컨슈머는 기본적으로  자동 커밋(enable.auto.commit = true)  상태로 설정되어 있습니다.
• 동작 방식: 컨슈머가 카프카로부터 메시지(예: 좋아요 +1 이벤트)를 가져오면, 일정 시간(보통 5초)마다 "나 이거
읽었음!" 하고 카프카 서버에 알아서 체크 표시(Offset Commit)를 남깁니다.
• 치명적인 문제점: 컨슈머가 메시지를 받아서 DB에  좋아요 +1 을 하려고 계산하던 도중에 서버가 뻗거나 DB 에러가
났다고 가정해 보겠습니다.
• 실제로는 DB 업데이트에 실패했는데, 카프카 쪽에는 이미 "읽었음"으로 체크가 되어버립니다.
• 서버가 재시작되어도 카프카는 다음 메시지부터 줘버리므로, 해당 '좋아요 +1' 이벤트는 영원히 유실(증발) 됩니다.


### 2. 수동 커밋 (Manual Ack) 이란?

자동 커밋 옵션을 끄고, 개발자가 코드상에서 직접 "지금 커밋해라!"라고 명령을 내리는 방식입니다.

• 동작 방식:
1. 컨슈머가 카프카에서 메시지를 가져옵니다. (카프카는 아직 체크 표시 안 함)
2. 컨슈머가 내부 로직(DB에  좋아요 +1  업데이트 및  EVENT_HANDLED  테이블에 이력 저장)을 수행합니다.
3. DB 트랜잭션이 완벽하게 성공(Commit)했을 때만, 코드 마지막 줄에서 카프카에게  ack.acknowledge()  를 호출하여
"진짜 처리 끝났어!" 라고 알려줍니다.
• 장점 (유실 방어): 만약 DB 처리 중 서버가 뻗어버리면 수동 Ack가 날아가지 않습니다. 카프카는 "어? 얘가 처리를 못
끝냈네?" 하고 판단하여, 서버가 살아나면 똑같은 메시지를 다시 보내줍니다. (At-Least-Once 보장)

Kafka의  enable.idempotence=true  설정과  event_handled  테이블은 서로 방어하는 장애의 구간과 주체가 완전히
다릅니다. 이 두 가지가 조합되어야만 진정한 '정확히 한 번 처리(Exactly-Once Processing)'가 보장됩니다.
이유를 알기 쉽게 세 가지 상황으로 나누어 설명해 드리겠습니다.
### 1.  idempotence=true 가 방어하는 구간 (프로듀서 ➡️ 브로커)

프로듀서(Outbox 스케줄러)가 Kafka로 메시지를 보냈는데, 네트워크 지연으로 인해 브로커로부터 성공(Ack) 응답을 받지
못했다고 가정해 보겠습니다.
프로듀서는 실패로 간주하고 **동일한 메시지를 재전송(Retry)**하게 됩니다. 이때  idempotence=true  설정이 되어
있다면, 브로커는 내부적으로 시퀀스 번호(PID + Sequence Number)를 식별하여 **"아, 아까 정상적으로 받았는데 응답만 못
받은 거구나. 중복 저장은 안 할게"**라며 걸러줍니다.
즉, 단일 프로듀서 세션 내에서의 네트워크 재시도에 의한 중복 발행만을 방어합니다.
### 2. 프로듀서 서버 자체가 죽었다가 재시작될 때 (방어 불가)
만약 Outbox 스케줄러가 Kafka에 메시지를 성공적으로 보내서 브로커에 저장이 되었는데, DB의  status 를  PUBLISHED 로
업데이트(UPDATE) 하기 직전에 서버가 다운되었다고 가정해 보겠습니다.
서버가 재시작되면 스케줄러는 DB에 여전히  INIT 으로 남아있는 해당 이벤트를 읽어 Kafka에 다시 전송합니다. 이때는
프로듀서가 재시작되면서 내부 세션 ID(PID)가 새로 발급되었기 때문에, Kafka 브로커는 이를 중복으로 인식하지 못하고고
토픽에 두 개의 똑같은 메시지가 적재됩니다.

### 3. 컨슈머가 죽었다가 재시작될 때 (방어 불가)

컨슈머가 Kafka에서 메시지를 읽고, DB의  PRODUCT_METRICS  통계를 성공적으로 업데이트(+1) 했다고 가정해 보겠습니다.
그런데 Kafka 브로커에게 "나 이 메시지 처리 완료했어(Offset Commit)"라고 수동 커밋(Ack)을 날리기 직전에 컨슈머
서버가 다운되었습니다.
컨슈머가 재시작되면, 커밋되지 않은 메시지를 다시 읽어오게(At-Least-Once) 되고, 통계 수치를 또 +1 하게 됩니다.
(결과적으로 +2가 됨)

### 💡 결론 (왜  event_handled 가 필요한가?)

위 2번과 3번처럼, 토픽 자체에 중복 데이터가 들어오거나 컨슈머 단에서 커밋 실패로 인한 중복 수신이 발생하는 것은
Kafka의  idempotence=true  옵션이 막아줄 수 없습니다.

따라서 컨슈머 측에서는 자신이 이 고유한 이벤트( event_id )를 처리했는지를 기억하고 있어야 하며, 이를 위해 통계
업데이트 트랜잭션과 동일한 트랜잭션 내에서  event_handled  테이블에  event_id 를 INSERT 해야 합니다.

질문해주신 **"DB 데이터와 메시지 간의 불일치 문제"**를 해결하는 것이 바로 Transactional Outbox 패턴을 도입하는 가장
큰 이유이자 핵심입니다.

제가 앞서  BEFORE_COMMIT 으로 처리했다고 말씀드린 부분은 **"Kafka로 메시지를 전송하는 네트워크 행위"가 아니라,
"DB의 Outbox 테이블에 발행할 이벤트를 데이터(row)로 Insert 하는 행위"**입니다.

정확한 워크플로우를 단계별로 설명해 드리면 다음과 같습니다.

1. 메인 트랜잭션 수행: 결제 실패/성공 데이터를 DB에 반영합니다.
2.  BEFORE_COMMIT  단계: 아직 트랜잭션이 커밋되지 않은 상태에서, 메인 트랜잭션에 합류하여 발행해야 할 이벤트를 DB의
    Outbox  테이블에  INIT  상태로 저장합니다.
    • 효과: 결제 비즈니스 로직이 롤백되면 Outbox 테이블 저장도 함께 롤백되고, 커밋되면 함께 커밋됩니다. 즉, DB
    데이터와 Outbox 이벤트 데이터 간의 100% 정합성이 이 단계에서 보장됩니다.
3.  AFTER_COMMIT  단계 (방금 구현한 릴레이 리스너): 트랜잭션이 DB에 완전히 커밋된 직후! 별도의 비동기 스레드(
    @Async )가 동작하여 Outbox 테이블에 저장된 데이터를 읽어와서 실제 Kafka 브로커로 메시지를 전송합니다.
4. 전송 성공/실패 처리:
   • 전송에 성공하면 DB의 Outbox 데이터 상태를  COMPLETED 로 변경합니다.
   • 만약 Kafka 쪽에 장애가 생겨 전송에 실패하더라도 트랜잭션 롤백은 발생하지 않으며(이미 커밋 완료됨), Outbox
   데이터는  INIT  상태로 DB에 안전하게 남아있습니다.
5. 스케줄러 (Fallback): 주기적으로 도는  OutboxScheduler 가  INIT  상태로 남아있는(발송에 실패한) 이벤트들을
   찾아내어 다시 Kafka로 재전송합니


   비즈니스 데이터의 정합성이 중요하고, 실패 시 전체를 취소해야 한다면 ➡️ BEFORE_COMMIT
   메인 로직은 무조건 성공해야 하고, 이벤트 처리는 알림이나 외부 시스템 연동 같은 부가 기능이라면 ➡️ AFTER_COMMIT

이벤트 핸들링 테이블(예: Outbox, Inbox 테이블)과 로그(History/Audit) 테이블을 분리하는 이유는 각 테이블이 가지는
'목적', '데이터 생명주기', 그리고 '성능 및 시스템 안정성' 측면에서 명확한 차이가 있기 때문입니다.

주요 이유는 다음과 같습니다.
### 1. 목적과 역할의 분리 (Separation of Concerns)

• 이벤트 핸들링 테이블 (Outbox / Inbox 등)
• 목적: 시스템 또는 MSA(마이크로서비스) 간의 메시지 전달 보장(At-Least-Once Delivery 등)과 트랜잭션 정합성
유지를 위한 운영(Operational) 목적입니다.
• 역할: 이벤트가 외부 브로커(Kafka 등)로 잘 발행되었는지, 혹은 잘 수신해서 처리했는지에 대한 '상태 제어' 용도로
쓰입니다.
• 로그 테이블 (Action Log, Audit Log 등)
• 목적: 사용자의 행동 이력, 상태 변경 내역, 에러 추적 등을 영구적으로 기록하기 위한 비즈니스 및 감사(Auditing)
목적입니다.
• 역할: 향후 CS(고객 서비스) 대응, 데이터 분석, 시스템 장애 시 원인 파악 등을 위해 과거의 기록을 남깁니다.


### 2. 데이터 생명주기 (Data Lifecycle) 관리의 차이
• 이벤트 핸들링 테이블은 '임시 보관소' 성격이 강합니다.
• 이벤트가 성공적으로 발행(Published)되거나 소비(Consumed)되고 나면 더 이상 필요가 없습니다. 따라서 주기적으로
삭제(Delete)하거나 완료 처리를 하여 테이블 사이즈를 작게 유지해야 합니다.
• 로그 테이블은 '영구 보관소' 성격이 강합니다.
• 데이터가 지속적으로 쌓이며 짧게는 수개월, 길게는 수년 단위로 보관됩니다. (예:  UserActionLog )


만약 이를 하나의 테이블에 합치면, 영구히 보관해야 할 방대한 로그 데이터 때문에 이벤트 발행 여부를 확인해야 하는
폴링(Polling) 쿼리의 속도가 심각하게 느려질 수 있습니다.

### 3. 성능 및 부하 격리 (Performance & Isolation)

• 이벤트 핸들링 테이블(특히 Outbox Pattern)은 별도의 백그라운드 스케줄러가 짧은 주기(예: 1초, 5초)로 미발행된
이벤트를 찾아내기 위해 지속적으로 조회(Select)하고 업데이트(Update) 합니다.
• 반면 로그 테이블은 주로 쓰기(Insert) 위주로 동작하며 조회는 특정 상황(어드민 확인 등)에서 간헐적으로 발생합니다.
• 이 두 가지를 하나로 합치면 지속적으로 쌓이는 거대한 데이터에 스케줄러의 빈번한 조회가 겹쳐 데이터베이스에
불필요한 락(Lock) 경합이나 병목 현상을 유발하게 됩니다.

### ❓ 질문 1. 선착순 진입 허용 및 수량 검증 정책을 어디서 처리할까요?

현재 가장 중요한 과제는 **"수만 명이 동시에 쿠폰 발급을 요청할 때, 100명이라는 수량 제한을 어느 시점에 어떻게
끊어낼 것인가"**입니다. 이를 위해 두 가지 접근 방식이 있습니다.

• 선택지 A: API(Producer)에서 Redis 카운터로 1차 검증 후 Kafka 발행
• 어떻게 동작하나요? 유저가 API를 호출하면, API 서버가 Kafka로 이벤트를 보내기 직전에 **Redis의 INCR(원자적
증가 연산)과 Set(중복 요청 필터링)**을 확인합니다. 카운터가 100을 넘지 않은 유저만 Kafka로 발급 요청 이벤트를
보냅니다.
• 장점: 빠른 실패(Fail Fast)가 가능합니다. 101번째 유저부터는 API에서 즉시 "선착순 마감되었습니다"라는 에러
응답을 줄 수 있습니다. Kafka나 DB에 불필요한 이벤트가 쌓이지 않아 시스템 부하가 최소화됩니다.
• 단점: 기존에 캐시용으로 쓰던 Redis를 핵심 비즈니스 로직(카운터)에도 의존하게  니다.
• 선택지 B: API는 무조건 Kafka에 발행하고, Consumer가 DB 락으로 검증
• 어떻게 동작하나요? API는 수량을 검사하지 않고 1만 명의 요청을 모두 Kafka로 던집니다. 이후 Kafka Consumer가
이벤트를 하나씩 꺼내어 DB 트랜잭션 내에서 비관적 락(Pessimistic Lock) 등을 걸고 수량이 100개 미만인지 확인하여
발급합니다.
• 장점: API(Producer)의 로직이 아무런 검증 없이 메시지만 발행하면 되므로 극도로 단순해집니다.
• 단점: 100명에게만 주면 되는데 1만 개의 이벤트가 Kafka 큐에 쌓이고, Consumer는 실패할 9,900건을 위해
무의미하게 DB 트랜잭션을 열고 수량을 확인해야 하는 막대한 자원 낭비가 발생합니다.

### ❓ 질문 3. 선착순 쿠폰 수량 메타데이터 관리는 어떻게 할까요?

질문 1에서 Consumer가 **"DB 락을 걸고 수량을 검증"**하는 방식을 선택하셨습니다. 그렇다면 DB가 선착순의 기준점
역할을 하게 되는데, 이때 한정된 수량(예: 100개)이라는 메타데이터를 어디에 보관할지 결정해야 합니다. 기존 2주 차
ERD의  COUPON_TEMPLATES  테이블에는 전체 수량을 제한하는 컬럼이 없습니다.

• 선택지 A:  COUPON_TEMPLATES  테이블에  total_quantity  및  issued_quantity  컬럼 추가
• 어떻게 동작하나요? 쿠폰 템플릿 엔티티 자체에 '총 발급 한도'와 '현재까지 발급된 수량'을 추가합니다. Consumer는
비관적 락(Pessimistic Lock)으로 해당 쿠폰 템플릿 행을 잡고,  issued_quantity < total_quantity 인지 확인한 후
수량을 1 증가시키는 방식입니다.
• 장점: ERD만 봐도 쿠폰의 메타데이터(한도와 누적 발급량)가 한눈에 파악되며, 어드민에서 쿠폰을 생성할 때 일관성
있게 관리하기 좋습니다. Consumer 로직(락 획득 후 수량 증가)도 매우 직관적입니다.
• 선택지 B: 컬럼 추가 없이, 발급 내역( COUPON_ISSUES ) 카운트로만 수량 검증
• 어떻게 동작하나요? DB 스키마는 건드리지 않고, 총 수량 제한은 애플리케이션 코드나 설정으로 둡니다. Consumer는
발급 전  SELECT COUNT(*) FROM coupon_issues WHERE coupon_template_id = ? 로 100개 미만인지 확인하고 발급합니다.
• 장점: 테이블 스키마를 변경하지 않아도 됩니다.
• 단점: 매번 발급 내역 개수를 세어야(COUNT) 하므로 DB 부하가 발생할 수 있고, 다수의 Consumer가 동시에 카운트할
때 정합성을 맞추기 위해 더 복잡한 락이나 트랜잭션 격리수준 제어가 필요합니다.

### ❓ 질문 2. 발급 완료/실패 결과를 유저가 확인하는 방식을 어떻게 할까요?

확인합니다.
• 장점: 백엔드에서 추가적인 상태 저장이나 새로운 API 엔드포인트를 만들 필요가 없어 구현이 매우 단순해집니다.
• 단점: 유저가 발급 실패를 명시적으로 알기 어렵습니다(목록에 안 나타나면 타임아웃 처리). 다만 질문 1에서
Redis로 앞단에서 걸러내기로 했으므로, Kafka로 넘어간 건은 Consumer 장애가 아닌 한 대부분 성공한다고 볼 수
있습니다.
• 선택지 B: 발급 요청에 대한 고유 ID를 부여하고 전용 상태 확인 API 만들기
• 어떻게 동작하나요? 발급 요청 시 백엔드가 고유한  requestId 를 응답해주고, 상태를 Redis에 임시 저장(상태:
IN_PROGRESS )합니다. 클라이언트는 새로운 API인  GET /api/v1/coupons/requests/{requestId} 를 폴링하여 상태가
SUCCESS 인지 확인합니다.
• 장점: "발급 진행 중", "발급 성공", "발급 실패(이유)" 등의 상태를 유저에게 가장 명확하게 전달할 수 있습니다.
• 단점: 요청 상태를 지속적으로 기록하고 업데이트하기 위한 Redis 키 관리와 신규 API 로직이 추가되어야 합니다.

매우 날카롭고 좋은 질문입니다! 설계 리뷰에서 이런 트레이드오프(Trade-off)를 짚어내는 것이 가장 중요합니다.
결론부터 말씀드리면, 기존의 낙관적 락과 이번에 도입한 비관적 락은 "보호하려는 타겟"과 "충돌 발생 확률"이 완전히
다르기 때문에 비관적 락 도입의 당위성이 매우 큽니다.

상세한 이유는 다음과 같습니다.
──────
### 1. 사실 관계: 기존 낙관적 락은 '발급'이 아닌 '사용'을 위한 것입니다.

기존 2주 차 ERD를 보면 낙관적 락( version  컬럼)은  COUPON_TEMPLATES (쿠폰 종류)가 아니라 ** COUPON_ISSUES (유저가
발급받은 개별 쿠폰 내역)**에 걸려 있었습니다.
• 기존의 낙관적 락: 유저가 결제 버튼을 실수로 두 번 눌렀을 때(따닥), 1장밖에 없는 내 쿠폰이 두 번 사용되는 것을
막기 위한 용도입니다. 이는 동일 유저의 실수이므로 "충돌 확률이 극히 낮아" 낙관적 락(Optimistic Lock)이 매우
적합했습니다.
• 과거의 발급: 선착순 수량 제한 자체가 없었기 때문에, 템플릿의 잔여 수량을 락으로 잡고 차감할 필요가 아예
없었습니다.

### 2. 선착순 발급에 비관적 락을 도입해야 하는 당위성
이제 요구사항이 바뀌어  COUPON_TEMPLATES  테이블의  issued_quantity  (현재 발급된 수량)를 +1씩 증가시켜야 합니다.
이 수량 업데이트에 낙관적 락을 쓰면 안 되고 비관적 락을 써야 하는 이유는 다음과 같습니다.
#### ① 극도로 높은 충돌 확률 (High Contention)

수만 명이 동시에 쿠폰 발급을 요청하고, 여러 대의 Kafka Consumer가 동시에 DB의  COUPON_TEMPLATES  한 줄(Row)을
업데이트하려고 덤벼듭니다.
• 낙관적 락을 쓰면: 10개의 Consumer가 동시에 수량을 읽고 +1을 시도할 때, 단 1대만 성공하고 나머지 9대는
OptimisticLockException 이 터지며 롤백됩니다.
• 결과: 실패한 9대는 트랜잭션을 처음부터 다시 시작(Retry)해야 합니다. 재시도하는 도중에도 또 다른 요청들이
들어오므로, 시스템 자원(DB 커넥션, CPU)만 엄청나게 소모하고 성공률은 바닥을 치는 처리량 저하 현상이 발생합니다.

#### ② 비관적 락(Pessimistic Lock)의 우위

• 비관적 락( SELECT ... FOR UPDATE )을 사용하면 DB 엔진(InnoDB 등)이 해당 Row에 락을 걸고, 다른 Consumer들을
순서대로 대기(Queueing) 시킵니다.
• 충돌이 발생하면 예외를 던지고 롤백하는 것이 아니라, 앞 트랜잭션이 끝날 때까지 찰나의 시간 동안 기다렸다가 바로
다음 작업을 이어갑니다.
• 무의미한 애플리케이션 레벨의 롤백/재시도(Retry) 코드를 짤 필요가 없으며, 트래픽이 몰리는 단일 자원(선착순 100개
카운터)에 대해서는 줄을 세우는 비관적 락이 압도적으로 빠르고 안정적입니다.

#### ③ 선착순(FCFS) 순서 보장

낙관적 락에서 롤백 후 재시도를 하게 되면, 먼저 온 요청이 재시도를 하는 틈에 나중에 온 요청이 먼저 성공해버리는
"순서 역전" 현상이 발생할 수 있습니다. 비관적 락은 락을 획득하기 위해 큐에 진입한 순서대로 처리되므로
"선착순"이라는 비즈니스 요구사항을 더 잘 지켜냅니다.

### 1. Redis 검증 로직의 원자성 확보 (Lua Script 도입 고려)
• 배경: 현재 우리 시퀀스를 보면 Redis에서 1)  SADD 로 중복을 체크하고, 2)  INCR 로 수량을 증가시킵니다. 트래픽이
초당 수만 건씩 몰리면 이 두 명령어 사이에 미세한 시간차가 생겨 카운트가 꼬이거나 원자성(Atomicity)이 깨질 수
있습니다.
• 참고 포인트: 두 명령어의 실행을 하나의 원자적 작업으로 묶고, Redis와 WAS 간의 네트워크 왕복(Round-Trip) 비용을
최소화하기 위해 Redis Lua Script를 도입하는 것을 추천합니다. (스크립트 한 번의 호출로 중복 검증과 수량 차감을
동시에 완벽히 처리할 수 있습니다.)
### 2. 비동기 환경의 정합성 붕괴 대비 (올리브영 "미발급 0%"의 핵심)
• 배경: API 앞단(Redis)에서는 선착순 100명 안에 들어서 202 응답을 줬는데, Kafka 브로커가 일시 장애가 나거나,
Consumer가 DB 락 대기 중 타임아웃(Exception)을 맞아 실제 DB( COUPON_ISSUES )에는 저장이 안 되는 상황이 발생할 수
있습니다. 유저 입장에서는 당첨인 줄 알았는데 쿠폰이 안 들어오는 최악의 경험(CS 인입)을 하게 됩니다.
• 참고 포인트:
• DLQ (Dead Letter Queue): Consumer에서 로직 에러나 DB 에러로 발급이 실패한 이벤트는 버리지 않고 별도의 에러
토픽(DLQ)으로 보내서 추후 수동/자동 재처리를 할 수 있게 해야 합니다.
• 대사(Reconciliation) 배치: 이벤트 종료 후, Redis의 성공 유저 Set(100명)과 실제 DB의 발급 내역(예: 98명)을
비교하여, 누락된 2명에게 쿠폰을 보상 발급해 주는 배치 스케줄러가 백그라운드에 존재해야 합니다.


### 3. Kafka 핫 파티션(Hot Partition) 주의

• 배경: Kafka 이벤트 발행 시  coupon_id 를 파티션 키(Partition Key)로 잡으면, 특정 선착순 쿠폰(예: 네고왕 90% 할인
쿠폰) 하나에 트래픽이 몰릴 때 Kafka의 특정 파티션 1개에만 메시지가 왕창 쌓이는 현상이 발생합니다.
• 참고 포인트: Consumer를 여러 대 띄워도 파티션 1개에 몰려 있으면 병렬 처리가 불가능해져 폴링 대기 시간이
길어집니다. 따라서 파티션 키를  user_id 로 설정하거나, 아예 키를 주지 않고 라운드 로빈(Round-Robin) 방식으로
분산시켜 모든 Consumer가 고르게 일하도록(Throughput 극대화) 구성해야 합니다.

### 4. 클라이언트 폴링 API 부하 분산

• 배경: 발급 결과를 알기 위해 유저들이  GET /requests/{requestId} 를 1초마다 폴링하면, 1만 명이 10번씩만 호출해도
10만 번의 Read 트래픽이 발생합니다.
• 참고 포인트: 이 상태 확인 API가 절대 DB를 쳐다보게 만들어서는 안 됩니다. 현재 우리가 수정한 다이어그램처럼, 상태
API는 철저하게 **Redis에 임시 저장된 상태(IN_PROGRESS / SUCCESS / FAILED)**만 단순 조회(GET)하도록 구성해야 커머스
메인 DB가 죽는 것을 막을 수 있습니다.
